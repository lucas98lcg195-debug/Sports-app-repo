# Sports-app-repo

A lightweight, ad-free personal scores app for NCAA football and baseball. It pulls live data from ESPN's public unofficial JSON API and shows scores, schedules, and box scores without any of the articles, ads, or clutter of the official ESPN app. It ships as a Progressive Web App, so it installs on an iPhone through Safari's Add to Home Screen option without going through the App Store.

## How it is built

The backend is a FastAPI application under `backend/`. It fetches data from ESPN's scoreboard, summary, and team schedule endpoints, trims each response down to the handful of fields the frontend actually needs, and stores the result in a small SQLite cache so the app never hits ESPN more often than once every thirty seconds. A background job keeps today's scoreboards refreshed on its own, polling every thirty seconds while a game is in progress and backing off to every five minutes once nothing is live.

The frontend under `frontend/` is plain HTML, CSS, and JavaScript with no build step and no framework. `index.html` shows today's games grouped by sport with each team's logo, score, and status. Tapping a team logo on the scoreboard opens that game's box score in `game.html`. From the box score, tapping a team logo opens that team's school page in `team.html`, and from a schedule, tapping an opponent's logo jumps to that opponent's school page in turn. Each game also carries a "Watch on ESPN" link straight to that game's real ESPN page, where ESPN's own sign-in and player live, this app never touches a password or streams video itself. A `news.html` tab shows a merged, filterable headline feed pulled from ESPN and a few other sports outlets, always linking out to the original article rather than reproducing it. `rankings.html` shows the AP Top 25 and `standings.html` shows conference standings, both for either sport. `search.html`, reached from a small icon in the header, finds any school by name. A manifest and service worker make the app installable and keep the static shell and team logos available offline, while live score and news requests always go to the network so nothing goes stale.

`team.html` is a full school page, not just a schedule: a sport toggle (a school's football and baseball programs are two separate ESPN teams under the hood) sits above three sub-tabs, Schedule, Stats, and Roster. Switching sport doesn't assume the two programs share an id, ESPN doesn't guarantee that, so the other sport's team is instead resolved by matching this school's name against that sport's full team list the first time it's needed, and cached on the page after that. If no match is found, that sport's tab just says so rather than showing the wrong school's data.

Tapping a player in the Roster sub-tab opens `player.html`, showing that player's season stats grouped the same way team stats are. Everything on that page except the stats themselves (name, jersey, position, headshot, class, height, weight) comes straight from the roster row's link rather than a second fetch, since the roster call already has all of it, only the stats need fetching fresh.

Any team can be starred as a favorite, from the scoreboard, a box score, or a team's schedule page, and favorited teams' games are pinned in a "My Teams" section above the scoreboard. There are still no accounts: favorites are tied to an anonymous id this device generates once and keeps in both localStorage and a cookie. `settings.html` shows a short, human-typeable recovery code for that id (an adjective and a noun, like `blue-dog`) and a field to type in a code from elsewhere, so the same favorites can be restored on this device after a storage wipe or brought over to a different one, without ever asking for a password.

## Running it locally

Install the backend dependencies with `pip install -r backend/requirements.txt`, then start the server from the `backend/` directory with `uvicorn main:app --reload --port 8000`. The FastAPI app serves both the API routes and the static frontend from the same process, so visiting `http://localhost:8000/` in a browser loads the scoreboard directly. There is no separate frontend server and no npm install to run.

## API routes

`GET /api/health` returns a simple status check. `GET /api/scoreboard/{sport}` returns today's games for `football` or `baseball`, or a specific day when given an optional `date` query parameter in `YYYYMMDD` form, each game including the TV or streaming channel it's on where ESPN reports one. An optional `conference` query parameter scopes the results to one conference, using the id ESPN itself assigns that conference. `GET /api/conferences/{sport}` lists the conferences available for that sport's dropdown, each with the id the scoreboard route expects. `GET /api/game/{sport}/{gameId}` returns box score data for a single game, including the line score, team stats, and scoring plays where ESPN provides them. `GET /api/team/{sport}/{teamId}/schedule` returns a team's full season schedule.

The conference list is a small static table in `backend/conferences.py` rather than something read from ESPN, since ESPN's scoreboard and summary payloads never name a game's conference back to the caller. The football ids are well established. The baseball list only covers the conferences shared with football, since the smaller baseball-only conferences are harder to confirm without hitting ESPN directly. Add to either list in that file if a conference is missing.

`GET /api/news` returns a merged, newest-first list of articles from every configured news source, or just one source when given an optional `source` query parameter. `GET /api/news/sources` lists the sources available for that dropdown. The source list lives in `backend/news_client.py`, mixing ESPN's own news endpoint with plain RSS and Atom feeds from a few other outlets, RSS being the format publishers put out specifically for this kind of aggregation. Each source is fetched independently and a dead or wrong feed URL is simply left out of the merged list rather than failing the whole tab, so if a source in that file never shows any articles, its feed URL is the first thing to check and fix.

Every article is also run through a relevance filter before it reaches the feed, keeping only stories whose headline or description mention football, baseball, Auburn, Mississippi State University, MSU, or the transfer portal. That keyword list is `RELEVANCE_KEYWORDS` in `backend/news_client.py`, plain text and easy to edit directly.

`GET /api/rankings/{sport}` returns the AP Top 25 (falling back to whichever poll ESPN lists first if it can't find one named AP), each entry with its rank, previous rank, and record. `GET /api/standings/{sport}` returns every team in one conference's standings, given a required `conference` query parameter using the same id as the conference filter. Since ESPN's standings response doesn't reliably use the same stat names across sports, each team's stats come back as whatever labeled columns ESPN actually provided rather than a fixed set, the same approach already used for box score team stats. `GET /api/teams/{sport}` returns every team for that sport, cached for a full day since team lists barely change, and backs the school search page, which filters that list entirely client-side.

`GET /api/team/{sport}/{teamId}/roster` returns that team's roster, flattening ESPN's response whether it groups players by unit (football's offense/defense/special teams split) or returns a flat list (as other sports sometimes do). `GET /api/team/{sport}/{teamId}/stats` and `GET /api/player/{sport}/{playerId}/stats` both return categories in the same dynamic, labeled shape rather than fixed fields, sharing one parsing helper in `espn_client.py` since ESPN's team and player statistics responses tend to follow the same category/stat structure. Roster is cached for six hours, both stats endpoints for one, since none of them need live-score cadence.

Both statistics endpoints turned out not to live under the same host and namespace (`site.api.espn.com/apis/site/v2/...`) as every other endpoint this app uses, confirmed by a 404 once this was actually deployed. Each now tries a short list of candidate URLs in order (`TEAM_STATS_URL_CANDIDATES` and `PLAYER_STATS_URL_CANDIDATES` in `espn_client.py`) and uses whichever one ESPN actually answers, rather than betting on a single guessed path. If stats ever come back empty again, that list is the first place to add another candidate.

The response shape itself was also confirmed against real data from `.../athletes/{id}/splits`, and it's not what the rest of this app's stats-shaped responses look like: stat names and values are flat, parallel arrays (`displayNames`, and a `stats` array of raw values) shared across every category, sliced by each category's declared `count` rather than each category nesting its own labeled stats, and the actual numbers live under `splitCategories`, in the group named `split`, in whichever entry is named `Season` (as opposed to situational splits like Home or Away). `_parse_espn_splits` in `espn_client.py` handles that shape and is tried first for both team and player stats; the earlier, more conventional category-nesting shape is kept as `_extract_stat_categories`, a fallback in case some sport or context still returns that instead.

## Highlight stats

The team Stats sub-tab and the player page each show a row of headline tiles above the full stat tables. For a team: win percentage (computed from that team's schedule, `W`/`L` results already fetched for the Schedule tab, no extra call) and, for football only, the team's passing, rushing, and receiving leaders. ESPN doesn't expose a "team leaders" endpoint this app has found, so `GET /api/team/{sport}/{teamId}/leaders` computes it: `backend/leaders.py` takes the roster, narrows to the positions that plausibly lead each category (only quarterbacks for passing, skill positions for rushing and receiving, rather than checking every player), and checks each candidate's own season stats, reusing the same cache entries the player page fills in, so a player already looked at elsewhere is free to check here. Cached for an hour like the other stats endpoints. Each leader tile links to that player's page.

For a player, the header shows position-specific numbers, e.g. total yards, completion percentage, and touchdown-to-interception ratio for a quarterback, computed entirely client-side from the same stats categories the full tables below already render, no extra fetch. The position-to-stat-labels mapping lives as `POSITION_KEY_STATS` in `frontend/app.js`. Only the quarterback entries are confirmed against real ESPN label text; the rest follow the same naming convention as a reasonable guess and may need a label corrected once seen against a real player at that position, the same kind of fix the stats endpoint itself needed twice before. A position with no curated entry, or one where none of its listed stats are actually present, simply shows no header row rather than guessing or fabricating a number, offensive linemen in particular tend to have no individually tracked stats in ESPN's data at all.

`GET /api/favorites`, `POST /api/favorites`, and `DELETE /api/favorites/{sport}/{teamId}` all take a `device_id` (query parameter for GET and DELETE, request body field for POST) identifying which anonymous device the favorite belongs to. `GET /api/device/code` returns that device's recovery code, generating one the first time it's asked. `POST /api/device/recover` takes a `code` and returns the device id it maps to, which the frontend then adopts as its own so the same favorites follow it. `backend/favorites.py` holds this logic along with the two SQLite tables (`devices` and `favorites`) and the adjective/noun word lists the codes are built from.

## Deploying

The app is a single Python process with no external database, so it deploys cleanly to Render's free web service tier straight from this GitHub repository. Point Render at the `backend/` directory, set the start command to `uvicorn main:app --host 0.0.0.0 --port $PORT`, and the same process will serve the API and the installable frontend at the resulting public URL. A custom domain from a registrar such as Cloudflare can be pointed at that Render service afterward if wanted, though it is not required to use the app.

## Scope

This is a single-user personal project. There are no user accounts, no authentication, and no multi-user features, and none are planned.
